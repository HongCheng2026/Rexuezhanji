# 养成系统如何科学地作用到战斗 —— 业界模式借鉴与设计建议

> 本文是**研究/方案文档**，不改动任何代码。目标是回答你截图里的三个问题：
> 1. 单体聚合函数（`combatStats.generateBattleLoadout`）该怎么科学地写？
> 2. 共享可变的 `profile` 大对象该怎么科学地归属？
> 3. 为了 HUD 一个战力数字反复全量聚合（`powerCalculator.calculateActivePower`）该怎么科学地避免？
>
> 结论先行：**三者是同一个问题的三面** —— 养成系统的"数值"应走「注册式贡献者管线 → 派生缓存（按哈希失效）→ 单一写入者的存档文档」这条业界通用链路。下面分别给依据和照搬方案。

## 1. 痛点一：单体聚合函数 → 借鉴「注册式 Stat Contributor 管线」

### 业界怎么做的（查证）
- **流放之路 / 暗黑破坏神 4（stat 聚合）**：每个 stat 有独立 ID（如 `maximum_life_+%`），来源只是"贡献者"（装备词缀 / 被动 / 光环 / 技能）。聚合引擎是**通用的**，它不认识具体来源；来源按 `flat`（加算）→ `additive`（增/减算）→ `multiplicative`（more/less，乘算）的桶顺序合并。新增一个系统 = 往桶里多扔几个 stat modifier，引擎代码一行不动。
- **Unity 数据驱动 stat 架构**：静态配置（`ScriptableObject`，只读、可多实例共享）与运行时状态（per-entity 的普通 class 副本）彻底分离。聚合 = 一串 **stat provider** 各自往一个累加器写，引擎不持有任何具体数值。
- **ECS（守望先锋 / Unity DOTS）**：Component 只装数据，System 只跑逻辑；"派生属性"是某个 System 在**输入变化时算一次**的结果，绝不每帧重算。

### 我们的效仿方案（JS 版）
定义 **`StatAggregator`**：一张已注册贡献者表 + 一个顺序合并器。`combatStats` 退化成"拉取贡献者 → 合并 → 冻结输出"，不再 import 各系统的内部知识。

```js
// 每个养成子系统只_register_一个贡献者，不再被上帝函数 import
StatAggregator.register("fighterUpgrade", function (ctx) {
  var f = ctx.fighterUpgradeApi.getLevels(ctx.profile);
  return {
    attack: { add: (f.attack - 1) * ctx.levels.attackPerLevel },
    maxHp:  { add: (f.hp - 1) * ctx.levels.hpPerLevel },
    armorPenetration: { add: (f.armorPenetration - 1) * ctx.levels.armorPenPerLevel }
  };
});

// 通用合并：先 flat 加算，再 additive 池，最后 multiplicative 池
function generateBattleLoadout(profile) {
  var ctx = buildContext(profile);          // 只取原始输入，不认识任何子系统
  var acc = StatAggregator.reduce(ctx);     // 顺序合并所有已注册贡献者
  return freeze({ finalStats: acc.finalize(), abilities: ..., autoSkills: ... });
}
```

- **收益**：新增一个养成系统（比如以后加"僚机羁绊"）= 注册一个 contributor，不动上帝函数。
- **顺带贴合你的架构规则④**：`combatStats` 不再硬依赖 `rosterEconomy/codexSystem/tacticalLoadoutSystem`，解耦程度反而更高。
- **注意**：战术装配（activeSlots / autoWeaponIds / skill grades）和武器快照不是"数值贡献者"，它们是**结构性装配数据**，应作为聚合器的"非数值产出"单独收集，别混进 flat/add/mult 桶。

## 2. 痛点二：共享可变 profile 大对象 → 借鉴「单一写入者 + 派生缓存不回写」

### 业界怎么做的（查证）
- **Unreal（`USaveGame` / `UGameInstance`）**：持久化数据存 `SaveGame` 子类（序列化 blob）；运行时状态（当前血量、buff、瞬时计时）活在 Actor / Component 里，加载时由存档重建。存档文档**自己不被运行时改来改去**。
- **Unity 数据驱动**：`ScriptableObject` 是**只读共享**配置；per-instance 的运行时副本才可变，**绝不改 SO 资产本身**（改了会在编辑器跨会话污染）。
- **ECS / DOP（数据导向）**：游戏状态 = 一组 Component；存档 = 序列化这些 Component，读档 = 反序列化。没有"一个被所有人又读又写的大对象"。
- **Web 范式（Flux / Redux / Elm）**：单一真相源，所有变更走 **reducer（纯函数）**，杜绝散落的 `obj.x = y`。这点在 JS 项目里尤其值得直接搬。

### 我们的效仿方案（JS 版）
**两层分离**是核心：

1. **存档文档（`profile`）**：仍是序列化 blob，但**只通过 `profileStore` 的"意图式 mutator"写入**：
   ```js
   profileStore.applyFighterUpgrade(profile, statType, level); // 唯一写 fighterUpgrades 的口子
   profileStore.spendGold(profile, amount);                    // 唯一写 resources.old 的口子
   profileStore.setEnergy(profile, value);                     // 唯一写 resources.energy 的口子
   ```
   禁止在任意模块里散落 `profile.resources.old = x` / `profile.fighterUpgrades.attack = y`。

2. **派生 / 缓存状态（绝不进 profile）**：`finalStats`、`battleLoadout`、战力数字 —— 算出来就放缓存（见痛点三），**绝不写回存档文档**。

- **所有权**：`profile` 归 `profile.js` + `profileStore` 所有；其他模块只拿只读视图或 typed API。你现在的 `fighterUpgradeApi.applyUpgrade` 已经是 `fighterUpgrades` 的唯一写者（方向正确），但 `generateBattleLoadout` 仍直接翻 `profile.scene/upgrades/...` 读取 —— **读取可以**（profile 是数据），但所有"写"必须收口到 store。
- **版本号**：store 每次写入 `bumpVersion()`，派生缓存据此失效（接痛点三）。
- **兼容约束⑧安全**：本方案**不改任何存档字段**，只改"怎么算 / 怎么缓存"，`rxgame_save_v5` / 玩家数据结构零触碰。

## 3. 痛点三：为 HUD 一个战力数字反复全量聚合 → 借鉴「派生缓存 + 失效 + 轻量路径 + 事件驱动」

### 业界怎么做的（查证）
- **暗黑 / 流放**：角色面板属性**算一次并缓存**；仅当输入变化（换装 / 升级 / 点被动）时才重算。事件驱动：`stats dirty` → 重算一次 → UI 读缓存。
- **Unity `FloatVariable.OnValueChanged`**：HUD 血条 slider **订阅**这个变量，数值变化时被动刷新；**绝不在 `Update()` 里轮询重算**。
- **ECS**：derived stats 住在某个 Component；System 仅当 dirty flag 置位时重算，不是每帧。
- **Reselect / 记忆化**：派生数据按 input 哈希缓存，input 不变就直接返回缓存。

### 我们的效仿方案（对得上你的代码，具体）
- **A. 拆分「战力分」与「战斗 loadout」**：新增 `powerCalculator.estimateActivePower(profile)`，只算 3 个核心数（战姬 + 战机 + 战机强化 + 图鉴加成的 `attack/maxHp/armorPenetration`），走**轻量路径**；完整 `generateBattleLoadout` 只在**真正开战**时调用。HUD 数字永不再触发战术 / 武器 / 技能全量解析。
  ```js
  function estimateActivePower(profile) {
    // 只取 finalStats 里那 3 个核心数，不解析 autoSkillSlots / abilities
    var core = computeCoreStats(profile); // 轻量，无战术装配开销
    return scoreStats(core);
  }
  ```
- **B. 按内容哈希缓存 battle loadout**：`DerivedStatsCache` 的 key = `hash({scene, upgrades, fighterUpgrades, shipRanks, pilotRanks, shipSkillLoadouts, activeSkillGrades, autoWeaponLevels, codexBonus})`。命中即返回；`calculateTotalPower` 当前调两次 `calculateActivePower`（基线 + 未强化）会**自然合并为一次**。
- **C. 事件驱动失效**：任何养成系统经 `profileStore` 写入后 `bumpVersion()`；cache 监听版本号失效。UI **订阅 store 变更事件**刷新 HUD，而非每次 render 重算。

```js
var DerivedStatsCache = (function () {
  var cache = null; // { hash, version, loadout }
  function get(profile, version) {
    var h = hashInputs(profile);
    if (cache && cache.hash === h && cache.version === version) return cache.loadout;
    cache = { hash: h, version: version, loadout: combatStats.generateBattleLoadout(profile) };
    return cache.loadout;
  }
  return { get: get };
})();
```

## 4. 三者如何组合（一张总图）

```
[养成子系统：pilot / ship / fighterUpgrade / codex / tactical / skill]
        │ 各自 register 一个 contributor
        ▼
[StatAggregator]  ── 顺序合并 flat→additive→multiplicative ──┐
        │                                                        │
        │                                        [非数值装配：abilities/autoSkills]
        ▼                                                        ▼
[DerivedStatsCache]  key = hash(输入) + store.version  ◀── [profileStore]
        │  命中即返回，未命中才跑一次完整聚合           │ 单一写入者；每次写 bumpVersion()
        │                                                        │
        ▼                                                        │
[HUD / 战力面板] 读缓存数字（订阅 store 变更事件刷新）      │
        │                                                        │
        ▼                                                        │
[开战时 battleRuntime] 取缓存 loadout → battleState.createPlayer
```

`profile` 始终只作**存档文档**，被单一写入者拥有；派生值永远不回写。

## 5. 落地顺序建议（不在此轮改代码，等你拍板）

| 步骤 | 动作 | 风险 | 收益 |
|---|---|---|---|
| 1 | 抽 `estimateActivePower` 轻量路径 | 极小 | 立刻消除 HUD 全量聚合 |
| 2 | 加 `DerivedStatsCache`（哈希 + 版本失效） | 小 | 消除 `calculateTotalPower` 的二次重算 |
| 3 | 抽 `StatAggregator` + 各 contributor | 中 | 根治上帝函数，新增养成系统零侵入 |
| 4 | 推 `profileStore` 意图式 mutator，收口散落写者 | 中 | 根治共享可变 blob 的所有权混乱 |

建议按 1→2→3→4 顺序，因为前两步收益大、风险小、且不与任何现有架构规则冲突；后两步是更大的重构，适合分系统逐步迁移。

## 6. 风险与注意

- **缓存一致性**：哈希必须覆盖**所有**影响 `finalStats` 的输入；漏算一项就会"战力不刷新"。建议用**显式输入清单** + 单测断言（改任意一项输入 → 缓存失效 → 数字变化）。
- **兼容约束⑧**：本方案不改 `rxgame_save_v5`、不改玩家数据结构、不改 `Shell/index.html`，纯属"计算与缓存方式"的重构，安全。
- **先缓存后管线**：务必先落地 1、2（轻量路径 + 缓存），再动 3、4（管线 + store），否则一次改太多既动聚合又动写入，回归面过大。
