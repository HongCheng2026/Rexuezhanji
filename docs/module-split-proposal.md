# 模块拆分与科学分配方案

> 目标：把"大厅四区"的 UI 归类，重排成"按领域凝聚力"的模块分配，实现**高内聚、低耦合**。
> 原则一句话：**room（模块）= 拥有"一份数据 + 一个业务责任"的最小单元；room 内部的 tab / 面板 / 左右栏只是 UI 组合，不是独立模块。**

---

## 一、先纠正一个根本误区：room ≠ UI 子面板

你提的"战机强化拆成 3 个子模块""好友拆成列表+私聊两个模块"，这里藏着最常见的耦合陷阱：

- **战机强化的「属性 / 主动 / 被动」** —— 它们操作的是**同一份 fighterUpgrade 数据**、共用同一个 `fighterUpgradeApi` facade。如果拆成 3 个 room，反而会让 3 个 room 都去依赖同一个 controller，**耦合更重，不是更轻**。正确做法：1 个 `upgrade` room + 内部 3 个 tab。
- **好友的「列表 / 私聊」** —— 点列表里一个人 → 右边立刻开聊。这俩是**强绑定的一组操作**，拆成 2 个 room 反而要互相传"当前选中谁"。正确做法：1 个 `friend` room + 左列表右聊天 2 个 pane。
- **邮件「公告 / 活动」左右栏、设置「音频/画面/性能」4 个 tab、商店「金币/钻石」2 个 tab、任务「每日/活跃」2 个 tab、成就「3 大类」** —— 全是**同一个 room 内部的 UI 组合**，不该升格成 room。

**判断口诀**：同一个数据、同一个责任 → 同一 room 内用 tab/面板分；跨了数据或跨了责任 → 才拆成新 room。

> 你原方案里"邮件 / 签到 / 好友 / 设置 分为单独模块"——其中**邮件、签到、设置现在就已经是独立 room 了**，真正要从 God View 里挖出来独立的只有**好友**（加上排行榜、聊天，三者都挤在 `socialFeaturePanelsView` 里）。

## 三、按"领域凝聚力"重新分组（替代"屏幕四区"）

屏幕位置（顶部/左列/右列/底部）是**导航布局**，不是模块归属。模块该按"数据归谁、责任是什么"分。重排后 **7 个领域**：

```
A. 玩家档案 Profile      —— 我是谁、我多强
B. 养成 Nurturing       —— 战姬/战机/强化/图鉴（服务战斗，支柱2）
C. 战斗 Combat          —— 关卡/无尽/结算（核心，支柱1）
D. 抽卡 Gacha           —— 星穹之翼（支柱3）
E. 经济 Economy         —— 商店/兑换/背包/兑换码
F. 社交 Social          —— 好友/排行榜/聊天（从 God View 拆出）
G. 系统/留存 Meta       —— 任务/活动/成就/签到/邮件/设置
```


## 五、必须点破的 3 个耦合风险

### 风险1：图鉴 vs 战姬/战机 gallery 的"重复查看"问题
你让 `codexRoom` 也加"战姬/战机图鉴"，但 `pilotGalleryRoom` / `shipGalleryRoom` 也展示战姬/战机。要避免**两处都能看自己单位**造成责任模糊：
- **Gallery（战姬/战机 room）= 可操作管理**：拥有、购买、设出战、进强化。是可写的。
- **Codex = 只读百科**：全单位（含敌人）的图鉴查阅 + 图鉴强化元进度。是可读的。
- 决策：Codex 里战姬/战机只做**静态查阅（属性/立绘/背景）**，不提供购买/出战按钮；购买/出战只在 Gallery。这样数据虽然同源（都读 `profile` + 配置），但**责任不重叠**。

### 风险2：活动（activityRoom）的归属
`activityRoom` 现在实质只是"无尽模式入口"。无尽是**战斗模式**，不是"活动"。建议：
- 无尽战斗本体归 **C 战斗域**（和关卡平级，都是 battle 的变体）。
- `activityRoom` 降格为**薄 hub**：放"无尽入口"按钮 + 未来限时活动位。它不拥有战斗逻辑，只做跳转。
- 这样战斗域完整地拥有"所有打法"，活动域只做入口聚合，互不持有。

### 风险3：设置（settingRoom）是"跨切面"，别让它变成小 God
设置里的音频/画面/性能，本质是**写一份 AppSettings 配置资产**（对应 Unity 里你那套 SO 配置）。它：
- 只读写 `settings` 资产，**不调用任何业务 room**；
- "兑换码"按钮只跳转 `redeemRoom`，不内联兑换逻辑。
守住这条，设置就永远是薄壳，不会膨胀。

## 六、和三大支柱的对应（验证分配是否合理）

```
支柱1 战斗  → 域 C（战斗）           核心，唯一价值出口
支柱2 养成  → 域 B（养成）           + 域 E 经济供养强化 + 域 D 抽卡供单位
支柱3 抽卡  → 域 D（抽卡）           高端单位入口

支撑域（不直接产出战斗价值，但黏住玩家）：
  域 A 档案（我是谁多强）
  域 F 社交（好友/排行/聊）
  域 G 系统（任务/活动/成就/签到/邮件/设置）
```

验证标准：**每个 room 都能一句话说清"它独占哪份数据、负什么责"，且不和别的 room 抢同一份数据的写权。** 上面 26 个 room 都满足。

## 七、落地建议顺序（先拆最痛的）

1. **第一刀：拆社交 God View** → 新建 `friendRoom` / `leaderboardRoom` / `chatRoom`，把 `socialFeaturePanelsView` 退场。这是当前最大的耦合炸弹。
2. **第二刀：定下 room vs tab 红线** → 把"战机强化 3 tab""设置 3 tab""商店 2 tab"等明确为**内部 UI**，不建多余 room。写进 `AGENTS.md` 当硬规则。
3. **第三刀：落地 codexRoom v2** → 真实图鉴 + 图鉴强化，并和 Gallery 划清"可写 vs 只读"边界。
4. **第四刀： redeem 与 setting 解耦** → 设置里的兑换码改成跳转。
5. 其余（签到日历、邮件左右栏、成就 3 类、商店 2 类）按你意见在原 room 内重做 UI 即可，不动模块边界。

## 八、一句话总结给你拍板

> **别按"屏幕位置"分模块，按"数据 + 责任"分。room 是独占一份数据的最小单元；tab / 面板 / 左右栏只是 room 内部的 UI 组合，永远不要为它们新建 room。** 你原方案里真正要"新建独立"的只有：好友（从 God View 挖出）、排行榜、聊天、图鉴强化；其余"拆分"绝大多数应落地为"原 room 内的 tab/面板重做"。
